# Local architecture — Phase 2B2

React now mounts the local collection interface. `src/ui/store.ts` owns a shared snapshot and recent event state; Binder and Pack Desk derive indexed summaries from that snapshot. Initial load, committed revision notifications and explicit successful commands trigger coalesced refreshes. Refresh rereads recent displayed events from the ledger rather than appending to a pre-restore cache, so same-tab and cross-tab replacement cannot retain an old timeline. Search/filter/view/dialog changes perform no repository reads. The repository focus fallback still reads one snapshot and refreshes the shared layer only if its revision differs. Existing commands retain collection-sized transactional validation.

Mutations take a synchronous busy lock before asynchronous preparation; the saving state yields to the browser before execution. Success is announced only after execute confirms transaction completion. Failures remain visible, refresh the baseline where possible, and never announce success. Reservation changes carry both entity and collection guards; unprotection requires an explicit per-lot checkbox. Undo is offered for the session’s latest confirmed undoable command and invalidated on a different revision; the repository still checks the head and row images atomically. Reload intentionally does not offer historical undo.

Native modal dialogs provide focus containment and Escape handling, restore focus on close and announce errors. Printing entry requires explicit identity attestation and source notes. Unknown copies always use unresolved lots; unknown treatment is preserved verbatim. No printing is inferred from names or images. No verified-provider claim is made for manually identified printings. Settings exposes full backup and guarded replacement. There is no network, demo auto-seeding, artwork or third-party component dependency. UI test hooks and direct fictional scale seeding exist only in the separate test entry.

## Retained Phase 1C storage architecture

Phase 0 commit 0fd2b8a remains the calculation baseline. The prior plan was read in place; no additional private implementation or data was extracted. Phase 1C did not add end-user screens, service worker, backend or runtime network calls.

`src/storage/indexeddb/repository.ts` implements CollectionRepository. IndexedDB is authoritative; there is no localStorage snapshot or memory fallback. `prepareCommand` clones and SHA-256 fingerprints the canonical payload outside the transaction. `execute` validates the input and fingerprint, then opens one readwrite transaction over all stores. It rereads current records, replay keys, versions and revision, applies changes to an isolated staging state, validates references/quantities, and writes state, aliases, event, changed-row batch, replay result and revision together. Success and notifications occur only after `oncomplete`. Request failures and aborts reject; no success is inferred from a successful `put` request.

Routine commands retain full-domain reads and validation, but compare records by primary key and write only changed puts/deletes. Unchanged cards, printings, lots, allocations and aliases receive no writes. Alias projections update only for changed cards. The readwrite transaction still spans all stores and serializes same-origin writers: relative additions can both commit; absolute changes require both entity versions and collection revision. No history is read on routine writes after the logical-size cache initializes. A derived `meta/archiveBytes` row tracks exact canonical archive byte size and history count atomically; initialization reads existing history once, migration invalidates it, and replacement resets it. Each change accounts for changed row bytes, array separators, metadata and appended ledger records. The cache is excluded from backups and is not a source of domain truth.

Full-state reads, clones, comparisons and validation still scale with collection size. This phase eliminates storage/write amplification, not all collection-sized CPU work.

`expectedVersions` uses `cards`, `printings`, `holding` or `unresolved` for entity versions. Every existing card/printing edit, reservation edit, allocation removal and reconciliation also requires `{entity:'revision', id:'collection', version:snapshot.revision}`. New record creation and relative quantity/allocation additions do not require an absolute revision baseline. Unknown commands and fields are rejected, including the future command variants in the Phase 0 union.

Lot keys are `[kind,id]`; no raw-ID join is permitted. Stored lots omit allocatedQty; snapshot reads derive it from allocation rows. Unresolved quick-add always remains unresolved. Known quick-add coalesces by exact printing, unknown condition and unsealed status. Explicit lot creation is available for sealed copies. Allocations can use a descriptive deck container, but deckPlanId must remain null until deck-plan records are implemented. Reconciliation moves only unreserved copies from an unresolved lot to a new exact-printing lot, retains condition/sealed status/location/notes and conserves ownership; reserved copies stay on their original compound reference. There is no automatic reservation migration or artwork inference.

Undo supports only the unchanged latest undoable command batch. Every repository mutation changes the head atomically; inverse application additionally checks affected row images before changing anything. Undo commits a compensating batch/event and advances surviving affected entity versions. Unchanged entities keep their versions; absolute editors still require collection revisions. Snapshot-format legacy undo advanced every surviving version, so compacted legacy batches carry `legacyUndo:true` to preserve both historical replay and future head inverse semantics. Undoing undo, skipping intervening commands and arbitrary historical undo remain unsupported. Delta batches carry complete changed record images, and operation payloads explain intent. Semantic backup validation reconstructs full historical states backward, replays each command, validates quantities/references and checks exact resulting changes without retaining expanded full-state history in memory.

Committed revisions are advisory notifications through BroadcastChannel; focus rereads provide a fallback. Notification failures cannot convert a committed save into a failure. Correctness does not depend on notifications. Database connections close on versionchange; blocked upgrades fail visibly and require older tabs to close.

## Database schema

The database is `community-collection-local`, currently version 3. Migration 0→1 creates the store layout and metadata. Migration 1→2 backfills exact printing identity keys and aliases and adds indexes within the upgrade transaction; an identity-index collision aborts the upgrade. Phase 0 opened no database. Migration 2→3 compacts each existing batch where smaller in the atomic upgrade transaction, preserving events, payloads/results, IDs and revisions; an abort leaves version 2 intact. No records are pruned. Opening a version 1 database runs both migrations. Domain metadata `schema:2` is retained because domain record shapes have not changed; database and backup schema versions advance to 3 for the history representation. Version 1 is the explicit initial-layout migration baseline, not a private database import.

| Store | Key | Implemented indexes / purpose |
| --- | --- | --- |
| meta | key | state: domain schema, monotonic revision, headBatch; archiveBytes: derived byte/count cache |
| cards | id | name; full card/alias source records |
| aliases | id (serialized card+normalized alias) | normalized, cardId; derived from cards |
| printings | id | unique serialized identity; cardId |
| lots | [kind,id] | cardId, printingId |
| allocations | id | [lotKind,lotId], deckPlanId |
| events | seq | batchId; sequence uses committed revision, gaps allowed |
| batches | id | unique revision; delta@1 changed-row before/after images (legacy snapshots accepted on restore) |
| operations | id | canonical payload, SHA-256 and original result |
| decks, deckLines, trades, tradeLines, quotes, providerMaps | id | Reserved extension stores, empty in Phase 1 |
| imports, artworkEntries, blobs | id | Reserved extension stores, empty in Phase 1 |

Provider mappings currently persist inside printing records, matching the Phase 0 domain type. Aliases and printing identity keys are reproducible storage projections. Reserved stores have no write API yet. Export refuses nonempty reserved stores rather than omitting unknown data. Future phases can add indexes and versioned records through migrations without changing compound lot identity or the command boundary; their commands and backup schema require explicit implementation/version review.

`src/interchange/backup.ts` provides export, strict parsing, preview and replacement. The pre-replacement recovery callback must complete before writes. Current revision is checked again in the replacement transaction. Every store is replaced atomically, including history/replay information; a failed transaction retains the old data. Replacement is never an additive acquisition import.

Storage diagnostics expose estimates and persistence requests without claiming browser retention guarantees. The application still requires a static secure origin or a suitable local development origin. File URLs and offline cold launch/PWA installation are not certified in Phase 1.

## Limits and verification boundary

Commands cap the serialized archive at 16 MiB minus 4096 bytes of envelope headroom, keeping all accepted command state within the backup size bound. Input supports at most 50,000 records in each domain/history array, 10,000 characters per text field, 200 per ID and 100 aliases/mappings. The archive bound and history count bound remain enforced, with no retention/pruning policy. Full-domain reads and semantic ledger validation remain performance limits. No history is silently pruned.

Phase 1B established the original 23 Chromium scenarios and storage-amplification baseline. Phase 1C results, additional regression coverage and measured scale limits are recorded in phase-1c-results.md.

Legacy snapshot batches remain intact when the explicit delta/legacy-undo markers would increase their size; this prevents migration or compatibility conversion from growing an already valid archive beyond its limit. Routine new commands always produce delta batches.

## Phase 2B1 data management

`src/ui/DataManagement.tsx` owns the Settings workflow. `src/data-management/worker.ts` opens its own repository connection and calls the existing export, preview and restore contracts. File reading, JSON parsing, canonicalization, checksums, semantic history replay, recovery export, and replacement validation/writes run in a dedicated module Web Worker. Only preview summaries and a completed download string cross to the UI. Download filenames (format plus source timestamp) are computed in the worker. Blob construction and browser download initiation remain on the main thread. Unsupported workers fail visibly instead of falling back to blocking main-thread validation.

The worker keeps the validated source and expected revision for the preview; the UI cannot supply an unvalidated archive to replacement. Explicit confirmation starts full revalidation and complete recovery export. Recovery retention uses the separate `community-pre-restore-recovery` IndexedDB database, version 1, `backups` store keyed by UUID with a creation-time index. Every recovery is added with strict transaction durability requested, its transaction completes, and its complete string is read back in a new transaction and compared before replacement can proceed. No existing recovery is deleted to make room. Quota, request, transaction or verification failure stops replacement. Recovery is outside the collection database so the atomic collection replacement cannot erase it. Settings offers the latest retained recovery for download; local retention is still subject to browser eviction and is not a substitute for external downloaded copies.

After retention, the worker pauses at a handshake. The main thread disables cancellation synchronously before acknowledging the irreversible stage. Before acknowledgment, cancellation terminates the worker with no collection writes. Messages from terminated or superseded workers are ignored, including already queued messages after cancellation. After acknowledgment, one guarded atomic replacement runs to transaction completion. Navigation and local mutations are disabled while work is active. A beforeunload prompt is requested during commit; browsers may ignore it, and an interrupted transaction retains IndexedDB atomicity. Unexpected worker failure reports no confirmed success and directs the player to reload before retrying. The UI announces restoration only after the commit result and collection/history reload. Session undo is cleared; the persisted source head semantics remain intact.

The preview displays source format/time, incoming card/printing/lot/copy/history/replay totals and current card/copy totals. It warns of complete replacement. A revision notification marks previews stale; the interchange recovery check and the final transactional revision check remain authoritative if notifications are delayed, missing or race with retention. Revisions advance beyond both databases, preserving cross-tab editor guards and replay protection. No validation checks or limits changed and no history is pruned. Expensive validation runs more than once by design; worker isolation improves responsiveness without claiming reduced execution cost. Progress names actual stages and never estimates percentages.

The browser test harness now bundles its UI as an ES module and fulfills worker assets in memory on its reserved test origin. Fault injection exists only in a separate test worker. Performance measures worker export, preview validation and restore separately while a 16 ms main-thread timer measures scheduling gaps. Fixture setup is excluded. Physical mobile hardware has not been certified.

## Phase 2B2 playsets, extras and trade preparation

`src/ui/CollectionTools.tsx` uses the existing `allCardStats` grouping once per shared snapshot and authoritative `cardStats` for ownership, extras and availability. Search, completion/classification filters and the three Extras views use this memory projection; printing lookups are memoized. Navigation resets local filters. The screen states its local-catalog scope and distinguishes ownership (including sealed/unresolved) from free deckbuilding copies. Default goals remain Standard=3 and Legend=1. The authorized custom keep-target completion rule changes `cardStats` to compare ownership against keep; unknown classification stays explicit even with an override. No persistent shape or replay semantics changed.

Keep editing uses existing guarded save-card. Trade editing uses existing guarded set-reservations, preserving the lot's protected quantity and all allocation references. Each form shows exact printing or unresolved identity, condition, sealed state, owned/protected/allocated/marked/free quantities and maximum mark capacity. Every save requires confirmation, including a multi-copy change or clearing marks. Multi-copy changes within one physical lot commit atomically; there is no multi-lot mass-mark action or automatic extra selection. Sealed lots may be marked under the unchanged reservation rules, but never contribute free deckbuilding copies. Stale edits fail through entity and revision guards; the shared store retains busy/error/commit and cross-tab handling and session head undo.

`src/interchange/trade.ts` explicitly projects only marked public trade fields, preserving each physical lot as its own row. CSV quotes every field, doubles quotes, uses CRLF and guards formula-leading values, including leading whitespace. Copyable plain text flattens line breaks and strips mention/backtick triggers; no posting service is called. Neither format contains private notes, storage locations, evidence notes or history. Export includes only forTradeQty, never additional protected/allocated copies. Browser CSV download and clipboard failures have visible feedback; text can also be selected manually. Full backup format/schema, strict worker validation and recovery replacement remain unchanged.

All matching rows currently render without virtualization. Full-domain command validation and snapshot refresh still scale with collection size. The Phase 2B2 measurements characterize one desktop Chromium host with a mobile-sized viewport, not physical-mobile certification. No deck planning, pending-trade receipts, external trading or Phase 2C implementation is included.

## Phase 2C catalog infrastructure (real-data gate blocked)

src/catalog/catalog.ts validates independently testable, versioned text-only releases and computes conservative candidates. src/catalog/install.ts runs only safe additions through the shared repository command path. A catalog-release command stages cards/printings and provenance associations, validates the whole state and commits changed rows, history, fingerprint/replay result and revision in the existing single IndexedDB transaction. Holdings and allocations are never touched. Same-version/different-content releases are rejected against retained operation history, and backup semantic validation checks this as well. Complete history retains the release manifest and explicit incoming-to-local choices. There is no additional catalog database to lose during backup/restore.

Startup loads the inventory before attempting a packaged install. A failed install leaves inventory available and shows retry; conflicting records defer to Settings review. No approved real release is currently enabled: the production null package displays BLOCKED and never seeds fictional fixtures. After a future approved package is installed, all search data comes from the existing snapshot without provider calls. No service worker or offline navigation cache is introduced; offline local metadata is distinct from guaranteeing a first app-shell load without cached assets.

Candidate rules use stable catalog associations for existing catalog printings; exact normalized names/aliases only nominate custom gameplay identities for review. They never prove a physical printing match. Printing candidates require the selected gameplay identity, exact set code and non-null string collector number, or an existing stable association/ID conflict. Matching remains case/string-sensitive for physical identity fields; β, zeroes and suffixes survive. Multiple candidates are ambiguous. Adoption requires equality of the established printingIdentity tuple (gameplay ID, set code, collector number, treatment, language); identity conflicts cannot be overridden. Rarity/promo/collector/set-name differences are shown for explicit metadata review. Existing managed metadata is not automatically overwritten. Custom card records remain verbatim when explicitly associated; no cross-card inventory merge is implemented. A later version may require renewed custom-card association review.

Explicit printing adoption keeps the **existing local primary key**. No lot moves, splits, deletes or acquisition events occur; protection, allocations, trade marks, condition, sealed status, location, notes and historical references remain unchanged. Local printing notes and original evidence remain; incoming evidence and metadata remain in the operation manifest. The catalog provider association maps incoming ID to the retained local record. Unsupported/ambiguous choices reject or defer; no fuzzy-name or artwork matching exists. Cancellation writes nothing. Review carries the captured revision and rejects stale approval; explicit reviews may be safely undone only under the existing unchanged-head safeguards. Repeat identical adoption changes no entity versions or ownership, although a deliberately resubmitted command may append an audited no-op operation. Automatic repeated installation performs no command when nothing new is eligible.

Incomplete manual printing identity (including an explicit unknown identity field) is stored as a zero-quantity provisional unresolved lot, retaining entered fields in notes; copies can be added directly to that provisional lot. It is never inserted as a fabricated exact identity. Complete user-created printings retain established exact uniqueness. The unknown-printing detail workflow reuses the original reconcile command: only unreserved copies move to a new exact lot, preserving condition/sealed/location/notes; reserved copies stay on their original unresolved reference. This policy is deliberately distinct from custom-printing catalog adoption, which leaves every lot intact.

Binder, Pack Desk, Playsets and Extras initially render at most 100 cards; explicit incremental controls reveal further results. Catalog review shows 50 relevant entries at a time. Native controls retain keyboard/focus semantics. These controls bound initial work, not the DOM after a user deliberately reveals every row. Calculations and filtering remain snapshot-derived; writes, validation, full history manifests and refresh still have collection-sized CPU costs. Large catalog installation/updates can stall the main thread; measurements and limits are in phase-2c-results.md. No new dependencies, network synchronization, provider pricing or remote inventory service exist.

## Local Archive integration (supersedes the null-package description above)

The default package is now the pinned, stripped local-catalog/catalog.json. scripts/extract-archive.mjs accepts only a SHA-256-matching committed cards.json supplied explicitly; it performs no network access and copies only allowlisted tracking metadata. scripts/build-archive.mjs applies src/catalog/archive.ts deterministically. The app imports only the generated metadata, never upstream scripts, images or full rules. Existing installCatalog handles automatic transactional first launch, idempotent reopen, zero ownership, conflict deferral and version safeguards. Existing user records/holdings are preserved. Settings retains provenance/review; no new database or backup format is introduced.

All 860 source printing references have unknown finish and uncertain evidence. Selecting one records a source-identified holding with explicitly unverified treatment; it does not independently verify a physical foil/stamp variant. Completely unknown copies still use unresolved lots. Incomplete custom printings still use the existing provisional unresolved representation. No provisional catalog ownership lots are seeded. Source variants keep their own IDs/set/collector/language and can be selected in Binder details or Pack Desk. Display labels no longer describe all catalog printing references as verified exact printings.

Local safety and public release are separate audit modes. Both retain all privacy/secrets/artwork/dependency checks and exact reviewed hashes. Release mode additionally fails while local Archive metadata and bundles remain unapproved. The local Git commit and dist directory must not be pushed, deployed or distributed.

## Phase 3A personal artwork

Personal imagery is optional browser data, not catalog data. The pre-existing artworkEntries and blobs object stores now contain personal association/provenance records and SHA-256-addressed Blob values. No schema upgrade is needed. Card and printing artMediaId fields remain untouched. A guarded artwork transaction changes only those two stores and the shared revision/cache metadata; it never writes quantities, printings, allocations, trade marks or domain history. Shared revisions invalidate stale writers and restore previews, including across tabs. The UI clears its existing undo affordance on a revision change rather than manufacturing an inventory event. Unreferenced blobs are collected atomically after replacement/deletion; shared blobs survive while referenced.

File selection uses a native file input accepting JPEG, PNG and WebP, including supported mobile photo libraries. A dedicated worker checks signatures against MIME, bounded dimensions from headers, decodes with browser orientation handling, scales proportionately to a 1600-pixel longest edge and a 320-pixel thumbnail, and re-encodes WebP. Canvas re-encoding drops original metadata, filename and EXIF location; original bytes are never persisted. Limits are 20 MiB input, 40 million pixels and 32768 pixels on either edge. Unrecognized headers within the first MiB fail closed. Animated inputs produce one still image. Processing requires createImageBitmap, OffscreenCanvas and WebP encoding; unsupported browsers fail visibly without changing data. ImageBitmap resources close after use.

Artwork association requires the exact informational privacy acknowledgment. rightsStatus remains unverified, source is personal-local, and timestamp, dimensions and optional user artwork-association evidence are retained. The resolver permits this explicitly identified local-display use without converting it to owner attestation or redistribution permission. Specific-printing artwork requires selection, evidence text and confirmation. Source printings stay provisional; exact artwork confidence describes an association only. Multiple candidates and generic special-printing fallback require review; Binder withholds imagery for those rows. Binder uses the chosen printing, an unambiguous owned printing when there are no unresolved copies, or a gameplay view. Generic/exact/missing labels and physical printing labels remain separate.

Binder reads association metadata on revision changes, fetching only thumbnail blobs for rendered cards. Native lazy image decoding does not require full images for tiles. Details fetch larger processed images, initially showing at most five associations with explicit incremental expansion. Object URLs are revoked on replacement, navigation, discard and unmount, including late asynchronous reads. Initial rendering remains 100 cards; explicit pagination preserves the existing bounds. Settings exposes a card picker and coverage list. Retail English is the initial browsing context; Beta, promos/special, other languages and all entries are explicit alternatives. Owned browsing spans contexts, and manually created cards remain visible. These are presentation filters, never destructive catalog edits.

Complete backups use community-media@3 in a .ncv binary container: 12-byte magic NCV-MEDIA-3 plus newline, four-byte big-endian manifest length, UTF-8 JSON manifest, the original community-backup@2 domain JSON, then raw blobs in manifest order. The manifest has a canonical SHA-256 checksum covering provenance, domain length and blob hash/type/length descriptors. Domain checksum/history semantics remain unchanged; every blob is independently hashed, signature/dimension checked and decoded. Limits: 4 MiB manifest, 16 MiB domain, 5000 associations, 10000 blobs, 256 MiB total media, 280 MiB complete file. Missing, corrupt, duplicate, orphaned or out-of-bounds media rejects the whole restore before writes. SHA-256 detects corruption, not authenticity or rights.

A binary container avoids base64 inflation, ZIP decompression bombs and new dependencies. Blob slices/references assemble and parse media without converting the library to strings or one giant ArrayBuffer. Validation hashes/decodes one bounded blob at a time in the existing backup worker. Collection data/history still require bounded in-memory JSON; IndexedDB implementation may buffer commits. This is bounded portability, not unlimited streaming storage. Recovery readback hashes one-MiB chunks. Pre-restore recovery retains the complete binary Blob and verifies it before the commit boundary. Collection, history, provenance and blobs replace together in the existing all-store transaction, with an authoritative revision guard. Quota/abort leaves the previous Vault unchanged. Recovery remains separately retained even when a later replacement fails. Legacy @1/@2 backups restore with zero media, explicitly replacing the whole Vault; the complete pre-restore recovery preserves any prior images. Legacy domain-only export APIs refuse when artwork exists unless explicitly used internally by the complete media adapter. Trade/collection metadata exports are not complete artwork backups.

## Offline shell (Phase 3B)

The Vite build plugin generates a versioned service worker and a closed list of shell files, including hashed app/worker assets and the locally authorized catalog in the app bundle. Installation uses a single `Cache.addAll` operation; failed installation deletes only that candidate cache. Activation removes only obsolete `ncv-shell-` caches. Inventory, media and recovery databases are never accessed by the service worker. No runtime image or catalog URL cache exists. Navigation serves the version's cached entry point; hashed files belong to that version. Deploy complete builds atomically on the isolated host and keep the origin stable.

The browser's normal waiting lifecycle controls updates: there is no skipWaiting or forced navigation. The update notice asks the owner to finish work, close all controlled windows, then reopen. This avoids mixing new application code with old editing clients or interrupting recovery retention. Existing transactional database version 3 and revision guards are unchanged. Catalog additions and reviewed identity conflicts retain their prior behavior. Uncached first launch offline remains a browser navigation failure. Do not use cache deletion or database clearing as an update procedure.
