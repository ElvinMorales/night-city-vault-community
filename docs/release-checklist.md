# GitHub Pages small community beta checklist

> **Historical pre-launch checklist (Phase 4C).** The reviewed public repository and first GitHub Pages deployment were authorized and published on 2026-11-16. The checkboxes below reflect the original planning record, not today's launch status. Current limitations and open hands-on checks are documented in the [community beta audit](community-beta-audit.md).

Phase 4C prepares a local candidate only. No repository creation, push or deployment is authorized. See code-licensing-review.md and catalog-distribution-review.md.

- [ ] Owner records actual usability results: find a real card, add an owned copy and special version, Undo, edit, download a full backup and restore it in a disposable profile. Phase 3C/3D engineering UX reviews exist; no completed end-to-end owner acceptance record is present. Do not relabel automated testing as owner testing. A reproducible material data-loss/security/core-function defect blocks beta; missing device coverage alone does not.
- [ ] Preserve the local development repository/history separately. Export the final reviewed commit into an empty independent repository, intentional public author identity, no development refs/tags. Review the exact exported files. Do not mirror this repository.
- [ ] In that snapshot run npm ci, npm run check and npm run audit:release. Required notices, private-data/secrets/asset/network/dependency checks remain mandatory. - [ ] Obtain separate owner authorization for public repository creation, push and GitHub Pages launch. Configure main checks and Pages environment protection; Actions source only; deploy dist after verification. Do not enable branch publishing to bypass checks.
- [ ] Before inviting players, test the live HTTPS project URL with disposable data: first launch, 151-card catalog, one add/edit, full backup/isolated restore, offline launch after caching, normal update after closing windows, correct worker scope and no unexpected network requests. Local automation cannot certify live hosting.
- [ ] Invite a small opt-in group, label as beta, identify a feedback channel and support expectations. Tell every tester that storage is local, unsynchronized and subject to browser eviction. Ask for a full .ncv backup (including photos) outside the browser before updates, clearing storage or switching devices. Do not collect private backups in public bug reports.
- [ ] Record physical iPhone Safari/Home Screen, Files, camera/HEIC, memory-pressure and VoiceOver results as tested/not tested, with device/iOS version; see iphone-manual-checklist.md. Track other Android/browser, accessibility and slow-device performance coverage as incomplete. Publish these limits rather than claiming certification. Unsupported import/device behavior should have a usable fallback; confirmed loss/corruption blocks beta.

Suggested beta wording: “This is an unofficial fan work, not approved or endorsed by WeirdCo or CD PROJEKT RED. Small community beta: browser/device coverage is incomplete. Collection data and photos stay in this browser; keep regular full .ncv backups outside it. The built-in catalog has 151 identities and 860 provisional source printings; physical treatments and completeness are not certified.”

Keep origin and path stable. IndexedDB storage is scoped to the origin, not the repository path; other projects on that hostname share a security boundary. Existing `community-collection-local` and `community-pre-restore-recovery` names must remain stable. Moving origin requires full backup/restore. Do not clear player storage to update the app. Workers/caches are project-scoped, navigation uses the canonical directory/hash model, and arbitrary pathname routes are unsupported by Pages. Live launch and owner testing are future execution steps, not completed by this local candidate review.

## Required GitHub settings before requesting deployment

After separate publication authorization, create the repository from the independent snapshot, never a mirror of development history. Before any deployment request, configure Settings → Environments → github-pages: required reviewer = the owner, deployment branches = selected branch main only, and disable administrator bypass. Leave Prevent self-review off if the owner will both dispatch and approve (otherwise a different authorized actor must dispatch). A named environment in YAML alone does not configure required reviewers.

Choose Pages source GitHub Actions. Require the verify job on main using a branch rule/ruleset; restrict workflow/settings edits to trusted maintainers. Set repository Actions variable PAGES_APPROVAL_CONFIGURED=true only after inspecting these settings. This is a setup interlock, not a substitute for environment reviewers. Push/PR runs verify only. Deployment additionally requires an explicit workflow_dispatch with deploy=true on main, passing all checks and the owner's approval of the waiting github-pages environment job. Neither repository creation nor first push approves deployment. Do not bypass a pending review.

GitHub references: [environment configuration](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments), [reviewing deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments). These are manual future account settings; none was configured or exercised locally.
